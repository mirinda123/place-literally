# Literal Name Map · 第一版方案

整理日期：2026-09-19。当前交付是数据与交互设计、种子 JSON 和翻译工作队列；尚未实现网站、搜索引擎或模型聚类。

产品的核心体验：选择一个地点，看到远处有哪些名字表达了相同或相近的意思。也可以从一个含义、一段描述出发，在地图上探索。

保留首页文字：

> Literal Name Map  
> The world has fewer names than you think.

标语放在地图旁作为简短引子。第一屏直接提供地图、搜索框和含义入口，不另做需要点击进入的宣传页。

## 1. 数据源结论

本次没有找到覆盖全球、可以直接把国家和城市按统一字面义分组的完整现成库。已有资源能解决地点定位和词源原材料；本项目需要建立的是“名称分析 → 含义 → 语义关联”这一层。

| 来源 | 可用内容 | 在本项目中的位置 |
| --- | --- | --- |
| [Wikidata](https://www.wikidata.org/wiki/Wikidata:Data_access) | 实体 ID、多语言名称、P625 坐标、P1705 原名、P138 命名对象 | 地点消歧与基础信息；结构化数据为 CC0 |
| [Wikidata P2441](https://www.wikidata.org/wiki/Property:P2441) | 部分名称的逐字翻译 | 优先补充来源之一；经常是名称 statement 的 qualifier，不能只查主属性；覆盖率尚未统计 |
| [GeoNames](https://www.geonames.org/export/) | 全球地名、别名、坐标、行政归属、人口等 | 扩大搜索和地图覆盖；[字段表](https://download.geonames.org/export/dump/readme.txt)没有系统词源字段，下载数据按 CC BY 4.0 署名 |
| [Wiktionary / Kaikki](https://kaikki.org/dictionary/rawdata.html) | 可批量下载的词典 JSONL，包括词源文字、模板和部分实体关联 | 词源原材料首选；需要筛选地名、消歧、提取释义及审核 |
| [OSM 词源标签](https://wiki.openstreetmap.org/wiki/Key:name:etymology:wikidata) | 地理对象的命名对象及词源标签 | 后期补充人物、纪念、移植命名；不等同于直译数据库 |

[Wiktextract](https://github.com/tatuylonen/wiktextract) 可提取 `etymology_text`、`etymology_templates`，但模板并不是完整统一的语义树。词典中同一个词可能有多个语言条目、多种释义和多个地理实体，不应按名字字符串直接连接坐标。

已有 [Open Etymology Map](https://github.com/Danysan1/open-etymology-map) 可参考：它用地图展示名字来源，尤其是街道、设施纪念的人或事。你的差异在于跨语言寻找同义与语义相近的地名。其代码为 GPL-3.0；是否复用代码可以在实现阶段决定。

建议原始数据按发布批次下载和处理，前端加载自己生成的版本化 JSON，不让每次地图点击都依赖 Wikidata 或 Wiktionary 的在线请求。

## 2. 核心交互

桌面采用地图主视图，左侧或底部放搜索与 Explore by meaning，点击后右侧打开名称卡片；手机用底部抽屉。国家使用代表性锚点和“国家”标签，古城使用“古城”标签。后续有边界数据时再增加边界高亮。

### 从地点出发

1. 用户搜索或点击已收录的 Naples。主图钉放大，卡片显示“正在分析 Napoli 的历史来源 Neapolis”。
2. 同一规范含义下的 Carthage、Novgorod 出现相同图标和颜色；所选地点增加外圈，避免认不出起点。
3. 提供“查看全部关联”以缩放到世界范围，避免每次点击都突然跳离用户刚查看的地区。
4. 点击另一个图钉，保留当前探索主题并替换详情卡；选“以此为起点”再重算关联。
5. 少量结果可以从起点画细线；较多结果使用图钉和列表，悬停某一结果时再画对应连线。主题成员不需要两两连线。

线表示语义关系，不表示迁徙路线、共同祖语或历史影响。

### 从含义出发

“New City / 新城”显示当前收录地点数，点开后显示该组地图与列表。之前示意的 127、84 等数字均为占位，不能作为真实全球统计。此次种子中，新城 3 个、白城 2 个、都城的同义归一组 2 个。

“河流／水”属于宽泛主题，“白城”属于组合含义：两者可以共存，但入口标注是“含义”还是“主题”，计数也随探索范围变化。

### 匹配范围

用三段控制 `同义 · 相近 · 主题` 起步，比未校准的连续相似度滑杆更容易解释。

| 范围 | 规则 | 例子 |
| --- | --- | --- |
| 同义 | 完整的被分析名称，经明确规则归一后同义 | New city / New town 归入新城；保留原译 |
| 相近 | 核心意义相近，但限定、粒度或用词不同 | 都城关联北方的都城、东方的都城；说明方向差异 |
| 主题 | 更宽的策展概念，共享部分语义 | 中国自称与都城可在“中心与都城”主题相遇；并非互为直译 |

同义结果用实心图钉，相近结果用空心图钉或虚线外圈；主题结果显示主题标签。不要只靠颜色传达差别。卡片写“共同概念：都城；区别：东方限定”，比一个难以解释的分数有用。

空白地图位置不一定有已收录的词源。点击未收录地点时，明确显示“这个名称尚未收录词源”；不能将没收录说成没有含义或全球没有同义地名。

## 3. 模糊聚类与语义搜索

采用“可追溯的原始释义 + 规范含义 + 可重叠的语义簇”。一个名称可以同时属于“北方”“都城”“中心”多个簇，不强迫每个地方只选一个分类。

`meaning_id` 是同义归一的稳定锚点，不承担全部搜索和模糊匹配。语义簇另外维护层级和成员理由：

```text
Naples → new city → 新的城镇 → 城镇 / 名字里的“新”
Tokyo → eastern capital → 都城及其方位变体 → 中心与都城
中国 → central country → 中心与都城（仅主题关联）
New York → new + York → 名字里的“新”（不属于新城）
```

同义、较窄、较宽、相关分别记录为 `equivalent / narrower / broader / related`。较窄/较宽是有方向的关系；单条相似关系也不能自动传递：A 接近 B、B 接近 C，不说明 A 与 C 同义。

搜索框统一支持地点名称与含义描述，结果区分“地点”和“含义相关”。示例行为：

| 输入 | 期望结果 | 排除误解 |
| --- | --- | --- |
| 那不勒斯 / Napoli / Naples | 定位到同一地点及对应名称 | 不重复放三个图钉 |
| 新的定居点 / new settlement | Naples、Carthage、Novgorod | 不把 New York 自动翻成新城 |
| 跟首都有关系的名字 | 首尔、京都、北京、南京、东京 | 检索名字的含义，不按现在的政治地位筛选 |
| 北方的都城 | 北京应比东都、南都更相关 | 方向词不能被“都城”这一泛词淹没 |
| 中心 | 在主题范围内关联中国自称与都城组 | 清楚标注这是主题关系 |
| 名字里有水的城市 | 按词源中的水相关概念搜索 | 本批种子无结果；不能因为一座城市临海就命中 |

实施分两步：

- 首先使用已审核概念、双语别名、人工语义簇，提供确定而可解释的检索。这支持已准备的释义和表达，不宣称理解任意句子。
- 需要自由改写与跨语言召回时，离线为每条名称分析生成文本向量，查询时生成同一模型的查询向量；结合名称匹配、语义距离、关键修饰词和用户选定范围排序。低相关结果允许不返回，不强制凑满结果。

向量文本以字面释义、词素、概念标签和必要说明为主。不要把经纬度、国家介绍、旅游文案混入语义表示，否则模型可能按地理和知名度找到“相似城市”。

模型只推荐候选分组，不自动把相近词义写成已确认的同义关系。`semantic_similarity` 与 `review_status` 分开：相似度不是词源正确的概率。本次种子是人工簇，没有运行 embedding，也没有伪造相似度分数。

后续保存模型名、版本、预处理规则、向量维度、数据版本。建立一小组中英查询及负例，检验“新”是否被漏掉、“北/南”是否混淆、“水相关”是否误判成“临海”；阈值和分组范围通过这些例子调整，而非提前规定一个通用数值。

## 4. 是否需要后端

推荐结构：**静态地图前端 + 离线数据构建；如果首版要求任意中英文自然语言搜索，再增加一个轻量搜索 API。**

| 路径 | 是否需要在线后端 | 代价与适用性 |
| --- | --- | --- |
| 预生成 JSON + 双语别名和语义簇 | 不需要 | 最适合验证地图体验与开放数据协作；自由表达能力有限 |
| 预生成地点向量 + 浏览器生成查询向量 | 不需要查询后端 | 可做真正向量检索，但用户首次要下载模型，需测手机内存、推理与兼容性 |
| 预生成地点向量 + 轻量 `/search` API | 需要一个查询服务 | 前端较轻，统一模型版本与中英效果；有托管、网络和调用成本 |

[Transformers.js](https://huggingface.co/docs/transformers.js/v3.8.1/index) 提供浏览器运行模型的途径，包括 WASM / WebGPU。它证明全前端可行，但不能据此保证所有手机上的加载体验。[multilingual-e5-small 模型卡](https://huggingface.co/intfloat/multilingual-e5-small/blob/main/README.md)可作为多语言检索评估起点；尚未选定模型或做效果测试。

如果把自由语义搜索作为首版核心，我倾向于轻量查询接口：小规模数据可随服务发布并直接比较向量，不必立即引入向量数据库。模型大小和运行时限会影响无服务器部署；也可由轻函数调用托管 embedding API。付费接口的私密密钥放在服务端，并给公开搜索加基本限流。

接口只需要返回分析 ID、排序结果、匹配概念、语义关系类型和版本。来源、词义与卡片文字来自已发布数据。相关性解释优先由匹配概念生成，不让语言模型临时编造词源故事。

```text
开源数据 / 词源原文
       ↓ 本地或 CI 批处理
消歧 → 提取 → 翻译草稿 → 人工复核 → 概念 / 语义簇 / 可选向量
       ↓ 发布同一 data_version
静态 JSON ─────────────────→ 地图前端
可选向量索引 → 轻量搜索 API ← 用户的自然语言查询
```

批量翻译、向量生成和聚类可以按需在本地或 CI 跑，完全不要求常驻业务后端。仅预计算地点向量还不够：任意新查询仍需要被编码。

当出现账号、在线编辑审核、用户收藏同步、频繁数据写入，或索引规模与延迟要求使直接扫描不再合适时，再扩展服务和数据库。[pgvector](https://github.com/pgvector/pgvector)是可考虑的后续选项，不是 MVP 前提。当前不承诺某个数量阈值，先测实际数据体积与设备。

## 5. 数据契约

附带 JSON 的核心链路是 `place → name → analysis → meaning / clusters`。

| 集合 | 关键字段 | 作用 |
| --- | --- | --- |
| `places` | `id`, `display_name`, `kind`, `geometry`, `external_ids` | 地点实体和图钉；GeoJSON 坐标顺序是 `[经度, 纬度]` |
| `names` | `id`, `place_id`, `form`, `language`, `role`, `valid_from/to` | 具体语言的名称、短名、内名、外名、历史名 |
| `analyses` | `name_id`, `analysis_layer`, `etymon`, `segments`, `source_gloss_en`, `meaning_id`, `source_ids` | 具体名称的一种解释；可允许同名多种竞争解释 |
| `meanings` | 稳定 ID、中英文显示文案、概念和归一规则 | 严格层面的语义锚点；更改译文不会改变关联 |
| `semantic_profiles` | 核心概念、修饰概念、语义文本、可选向量 | 后续模糊检索的输入，不含地理距离 |
| `semantic_clusters` / `cluster_memberships` | 簇标签、父簇、成员关系、理由 | 多重归属和宽窄关系 |
| `semantic_edges` | 两个分析 ID、关系、解释、方法 | 有方向或无方向的显式关联，不能默认同源 |
| `sources` | 条目 URL、所阅页面、章节、访问时间、修订信息、许可、署名 | 证据与再利用来源 |

`analysis_layer` 区分现代字面组成、完整词义、历史词源；不是每个名字都应该强制拆成两个词。国家与城市可跨类型关联，但语义归一不能忽略国、城、山等核心概念。

词源证据、语义归组和翻译分别保留审核状态。用户界面用“有出处，待复核／已核验／有争议”等状态，不使用没有定义的 95% confidence。多个有争议解释可并列显示，默认不参与确定的同义组。

## 6. 种子数据与批量翻译

本次包含 **12 个真实地点、13 条名称记录、12 条释义分析、7 个规范含义、6 个可重叠语义簇**。

| 地点 | 分析的名称或词形 | 规范含义 / 用途 |
| --- | --- | --- |
| Naples | Napoli → Neapolis | 新城 |
| Carthage | 古代腓尼基名称 | 新城；地点标为古城 |
| Veliky Novgorod | 通称 Novgorod | 新城；完整名字还含“伟大的”限定 |
| Belgrade | Beograd | 白城 |
| Belgorod | Belgorod / 历史词形 | 白城 |
| Seoul | 서울 | 都城 |
| Kyoto | 京都 | 都城 |
| Beijing | 北京 | 北方的都城 |
| Nanjing | 南京 | 南方的都城 |
| Tokyo | 東京 | 东方的都城 |
| China | 中国／中國 | 中央之国；英文 China 独立记录且尚无分析 |
| New York City | New York | 新＋York 专名；用于检验不要误并入新城 |

逐条词源来源见 JSON 的 `source_ids → sources`，不是凭空虚构词源的 mock。但它们仍是原型种子：词义已找到出处，翻译与归组未经过专家审核；所有坐标都是手工近似演示锚点，外部地点 ID 暂空，不能当作已验证的全球底表。

- `literal-name-map.seed.json`：可供后续前端使用的数据契约样例，含搜索预期例子和人工语义簇。
- `translation-draft.jsonl`：每行一个名称分析，保留原始释义、来源、待复核中文和只读含义 ID。

后续翻译时按 `id` 合并结果，填写 `literal_zh_reviewed` 和 `translator_note`。译者可以提出分组更正，但不要靠翻译程序自动重写 `meaning_id`、坐标或来源。翻译改变展示文本，审核后的语义更正则产生新的数据版本。

空的 `literal_zh_reviewed` 表示尚未人工确认，不代表数据错误。正式数据导入时还应保存准确词典条目的 revision ID 或 dump 日期；本批只记了访问日，未声称锁定源页面版本。

Wiktionary 派生内容需要保留来源署名、修改说明与适用的 CC BY-SA 许可；Kaikki 的解析工具是 MIT，不意味着词典内容是 MIT。参见 [Wikimedia 使用条款第 7 节](https://foundation.wikimedia.org/wiki/Policy:Terms_of_Use/en#7._Licensing_of_Content)。将代码许可和词源内容许可分别记录即可。本批词源改编内容已逐条带有来源与署名字段。

## 7. 接下来的实现顺序

1. 用这批种子实现地图选择、图钉联动、原始名称卡片和三档匹配范围，验证探索体验。
2. 加入地点搜索、语义簇搜索；如果要求自由中英文描述，同时做轻量 `/search` 接口的效果试验。
3. 扩充有出处的词源数据，建立导入、翻译、审核与版本发布脚本；前端继续消费相同契约。
4. 用真实查询评估向量检索，再决定模型、混合排序、聚类阈值以及是否需要数据库。

当前已做的数据校验包括：ID 与引用、坐标范围、三个同义组计数，以及 New York 不进入新城、东京不进入无方向的都城同义组、英文 China 不继承中国内名词义。这些是数据与语义边界检查，不代表搜索模型已经通过测试。
